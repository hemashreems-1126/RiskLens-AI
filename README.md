# RiskLens AI

**Autonomous Payment Risk Investigation & Decision System**
Built for the Razorpay AI Buildathon 2026 — AI Risk Manager track.

RiskLens AI is an AI-powered payment risk investigation system. It detects suspicious transactions, investigates them using specialized AI agents, evaluates the evidence, recommends Allow/Review/Block, and creates an explainable audit trail.

All data in this project is **synthetic**. No real Razorpay data, customer data, or payment data is used anywhere.

---

## Why we built it

A fraud model can flag a transaction as suspicious, but a flag alone doesn't explain *why* it's suspicious, what evidence supports that, or what should happen next. RiskLens AI closes that gap by running every flagged transaction through a real multi-agent investigation before a human ever sees it — so the analyst gets a full case file, not just a red dot.

## Problem

Payment platforms process huge volumes of transactions. Anomaly detectors are good at finding statistical outliers but bad at explaining them, and a raw score gives an analyst nothing to act on.

## Solution

RiskLens AI pairs a deterministic fraud detector (Isolation Forest + rule engine) with a LangGraph multi-agent investigation pipeline. Each agent gathers **factual** evidence using deterministic tools; a deterministic risk engine turns that evidence into a 0–100 score; and only the *explanation* is generated by an LLM (Groq) — never the score or the decision.

## How it works

```
Transaction → Fraud Detector → LangGraph Planner
  → Evidence / Behavior / Network / Compliance Agents
  → Shared Case Memory → Risk Assessment (deterministic score)
  → (loop back to evidence if insufficient, max 2 loops)
  → Human Reviewer → Decision (ALLOW / REVIEW / BLOCK)
  → Explainability (Groq) → Audit Report → Human Feedback
```

See [`docs/architecture.png`](docs/architecture.png) for the full diagram.

### AI design principle

The LLM (Groq) **never** invents the risk score. It only reasons, plans investigation flow, and explains findings in plain language. Every number — anomaly score, risk score, thresholds, and the final ALLOW/REVIEW/BLOCK policy — comes from plain, auditable Python in `backend/app/risk/`.

## Technology

| Layer | Choice | Why |
|---|---|---|
| Frontend | React + Tailwind + Vite | Clean, fast investigation dashboard |
| Backend | FastAPI | Connects frontend to the AI/risk backend |
| Orchestration | LangGraph | Real state graph with conditional loops, not a disguised script |
| LLM | Groq only | Fast inference; the only LLM provider used anywhere in this project |
| Anomaly detection | scikit-learn Isolation Forest | Detects statistical outliers in transaction behavior |
| Rules | Deterministic Python | Explainable, auditable compliance/velocity/amount checks |
| Database | PostgreSQL + SQLAlchemy | Structured storage for transactions, investigations, audit logs |
| Containerization | Docker + Docker Compose | One command, no manual setup |

## Mock / offline mode

If `GROQ_API_KEY` is not set (or `FORCE_MOCK_LLM=true`), the Explainability Agent automatically falls back to a clearly-labelled offline placeholder instead of a live Groq call. **Every part of the system — detection, all four investigation agents, risk scoring, decisions, review, audit, evaluation — works fully in this mode.** This means you (or a judge) can run and demo the whole pipeline with zero API key. The UI marks any investigation run this way with an "AI reasoning: offline/mock mode" badge, and it's recorded in the audit trail (`llm_mode`) — never disguised as a live result.

If Groq is unreachable mid-investigation (network issue, invalid key, rate limit), the same fallback kicks in automatically rather than crashing — see "Failure Recovery" below.

## How to run on Windows

You need: **Docker Desktop**, **VS Code**, and a **Groq API key** (optional — see Mock Mode above).

1. Install and start **Docker Desktop**.
2. Open the extracted `RiskLens-AI` folder in **VS Code**.
3. In the project root, copy `.env.example` to `.env`.
4. Open `.env` and paste your `GROQ_API_KEY` (or leave it blank to run in mock mode).
5. Open a PowerShell terminal in VS Code and run:

   ```powershell
   docker compose up --build
   ```

6. Once it finishes starting, open your browser to:

   - Frontend dashboard: **http://localhost:4173**
   - Backend API docs: **http://localhost:8000/docs**

The first startup automatically creates the database tables, generates synthetic demo transactions, and runs the fraud detector to populate alerts — the dashboard is never empty. You can regenerate fresh demo data any time with the "Reset demo data" button on the dashboard.

If Docker Desktop isn't running, start it first — `docker compose` will fail with a connection error otherwise.

## Demo flow

1. Open the dashboard — see suspicious transactions already flagged.
2. Go to **Investigations**, click **Investigate** on any alert.
3. Watch the timeline: Planner → Evidence → Behavior → Network → Compliance → Risk Assessment → Decision → Explainability → Audit.
4. If risk is MEDIUM/HIGH, submit a human review (Allow / Block / Escalate).
5. Submit feedback on whether the decision was correct.
6. Check **Evaluation** for held-out test metrics, and **Audit** to pull the full audit trail for any investigation ID.

## Evaluation

The synthetic dataset carries a ground-truth `is_fraud` label (since fraud patterns were injected deliberately). We split it into TRAIN and a **held-out TEST set**, fit the detector on TRAIN only, and report precision/recall/F1/false-positive-rate/confusion-matrix **on TEST only** — visible on the Evaluation page and via `GET /api/evaluation`.

> These metrics are measured on a held-out synthetic test set and do not represent production accuracy.

False-positive and false-negative costs are **configurable, illustrative assumptions** (see `.env`), not real business figures.

## Failure recovery

- If Groq is unavailable, the system falls back to offline/mock explanations rather than crashing, and the investigation is still fully completed and auditable.
- If the risk assessment stage finds evidence insufficient, the graph loops back to gather more (bounded to `MAX_INVESTIGATION_LOOPS`, default 2). If still insufficient after the max, the case is routed to **REVIEW** rather than an automated BLOCK.
